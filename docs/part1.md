# חלק א׳ – זיהוי בעיה ותכנון פתרון

## 1. הבעיה

### האתגר
אתר הוראות תכ"ם מנגיש כ-420 הוראות מחייבות לכלל משרדי הממשלה, אך **התוכן עצמו אינו נגיש לחיפוש**:

- **התוכן נעול בקבצי Word.** ה-API של האתר (`/api/Document`) מחזיר מטא-דאטה בלבד: שם, מספר, פרק, מילות מפתח ותאריכים. טקסט ההוראה קיים רק בקובץ ‎.docx שיש להוריד ולפתוח.
- **החיפוש אינו קורא את הטקסט.** החיפוש החופשי מתבצע בדפדפן על 4 שדות בלבד: שם, תיאור, מילות מפתח ומספר. בנוסף, **כל** המילים שהוקלדו חייבות להופיע **באותו שדה**, כמחרוזת זהה. לכן ניסוח שונה מעט מזה של מנסח ההוראה מחזיר 0 תוצאות.
- **מילות המפתח, התחליף היחיד לטקסט, חלקיות.** ל-78 מתוך 418 הוראות אין מילות מפתח כלל. שדה התגיות ריק ב-100% מהמסמכים, ולכן מסנן "תגיות" במסך אינו מחזיר דבר. אין טיפול במילים נרדפות.

### מדידה
הרכבתי 20 שאלות מעשיות מפרק 1 (ביצוע תקציב), ולכל אחת ההוראה והסעיף הנכונים. לאחר מכן הרצתי עליהן העתק מדויק של לוגיקת החיפוש של האתר, על נתוני האתר עצמו:

| אופן החיפוש | ההוראה הנכונה נמצאה |
|---|---|
| שאלה בשפה חופשית ("תוך כמה ימים צריך לשלם לספק") | **2 מתוך 20** |
| 2–3 מילות מפתח ("איחור בתשלום", "כספת", "מקדמה לספק") | **8 מתוך 20** |

דוגמאות:
- **"איחור בתשלום"** → 0 תוצאות. הוראה 1.4.3 משתמשת במונח "עיכוב בתשלום".
- **"מקדמה לספק"** → 0 תוצאות, אף שקיימת הוראה 1.4.5 "תשלום מקדמות". המחרוזת "מקדמה" אינה מוכלת במילה "מקדמות".
- **"כספת"** → 2 הוראות לא רלוונטיות (מע"מ ביבוא, תשלומים במט"ח), ולא הוראה 1.10.1 על שמירת מסמכים כספיים בקופות ביטחון.
- **"שרשרת הרכש"**, ביטוי מתוך גוף הוראה 1.4.3 → 0 תוצאות.

### על מי זה משפיע ולמה כדאי לפתור
- **המשתמשים:** חשבי המשרדים וצוותי החשבות, אנשי רכש, יועצים משפטיים, ובמידה מסוימת גם ספקים.
- **המחיר היום:** מי שיש לו שאלה מעשית צריך לנחש איזו הוראה רלוונטית לפי הכותרות, להוריד קובץ Word ולחפש בתוכו, ולעיתים לחזור על כך עם כמה הוראות.
- **הסיכון:** ההוראות מחייבות. הוראה שלא נמצאה, או נמצאה בטעות, עלולה להוביל ליישום שגוי, למשל בהתנהלות מול ספקים, בתשלומים או בערבויות.

## 2. הפתרון – Takam Navigator

מנוע חיפוש שקורא את **תוכן** ההוראות ומחזיר את **הסעיף המדויק** שעונה על השאלה, גם כשהיא מנוסחת במילים של המשתמש.

- **פותר את נעילת התוכן:** הטקסט מחולץ מקבצי ה-Word ומפוצל לסעיפים לפי המספור המקורי (2.1, 2.12...). המספור מחושב מהגדרות הסגנונות במסמך, כפי ש-Word מציג אותו.
- **פותר את מגבלות החיפוש:** החיפוש מתבצע על הטקסט, והתוצאות **מדורגות לפי רלוונטיות**, במקום לדרוש שכל המילים יופיעו באותו שדה.
- **פותר את מגבלות מילות המפתח:** חיפוש לפי **משמעות** (embeddings) מוצא גם מילים נרדפות ("איחור" ↔ "עיכוב", "כספת" ↔ "קופת ביטחון"), בלי תלות במילות מפתח ידניות.
- **התוצאה המוצגת:** "הוראה 1.4.3 › סעיף 2.1", קטע מודגש מתוך הטקסט, מספר מהדורה וקישור לעמוד ההוראה באתר הרשמי. כשאין התאמה מספקת, המערכת מציגה "לא נמצאה הוראה מתאימה" ולא תוצאות אקראיות.
- **ללא מודל שפה מחולל (LLM).** המערכת לא מנסחת תשובות אלא מפנה למקור. כך נמנעות "הזיות", אין עלות שוטפת, והמידע אינו נשלח לצד שלישי.

**מדד הצלחה:** אותן 20 שאלות יורצו על הפתרון, בהשוואה לאתר הקיים. נבדוק אם ההוראה והסעיף הנכונים נמצאים ב-5 התוצאות הראשונות, ואם השאלה שאינה קשורה לנושא מחזירה "לא נמצא".

## 3. התכנון הטכני

### ארכיטקטורה

<div dir="ltr">

```
 takam.mof.gov.il  (/api/Document, /api/DocumentVersion, DownloadDocument)
        │  ingestion – console app, local cache of .docx files
        ▼
 Takam.Ingestion
   ├─ Takam API client (HttpClient)
   ├─ .docx parser (DocumentFormat.OpenXml) → numbered sections
   ├─ Hebrew normalizer (quotes, niqqud, prefixes ו/ה/ב/ל/מ/ש/כ)
   └─ Embeddings (ONNX Runtime + multilingual-e5-small, local)
        ▼
 SQLite:  sections + metadata  |  FTS5 index (BM25)  |  vectors (BLOB)
        ▼
 Takam.Api (ASP.NET Core Minimal API)
   GET /api/search?q=...   GET /api/sections/{id}
   hybrid search = BM25 + cosine similarity → Reciprocal Rank Fusion
        ▼
 takam-navigator-ui (Angular, RTL)
   search box · ranked results (directive › section, highlighted snippet, official link) · section view
```

</div>

### רכיבים מרכזיים
1. **קליטת נתונים (Ingestion):** שולפת את רשימת ההוראות הבתוקף ואת המהדורה הנוכחית של כל אחת, ומורידה את קובץ ה-Word עם מטמון מקומי. הרכיב רץ כתהליך batch, בנפרד מהשרת, ולכן אינו תלוי בזמינות האתר בזמן חיפוש.
2. **פענוח ופיצול לסעיפים:** קריאת פסקאות וטבלאות, חישוב המספור ההיררכי מהגדרות הסגנונות, ניקוי שאריות Word (שדות `REF`) וזיהוי נספחים. כל סעיף נשמר עם ההוראה, מספר הסעיף, הכותרת, המהדורה, התאריך והקישור.
3. **אינדוקס כפול:**
   - **אינדקס מילים** (SQLite FTS5, דירוג BM25) עם משקלים: כותרת > מילות מפתח > כותרת סעיף > גוף הטקסט. מדויק למספרים ולמונחים.
   - **אינדקס משמעות** (וקטורים ממודל רב-לשוני שרץ מקומית). מוצא מילים נרדפות וניסוחים שונים.
4. **מנוע חיפוש היברידי:**
   - שאילתה שהיא מספר הוראה (1.4.3) מובילה ישירות להוראה.
   - בשאר המקרים מבוצעים נרמול, חיפוש בשני האינדקסים ומיזוג התוצאות ב-RRF.
   - סף ביטחון קובע מתי להחזיר "לא נמצא".
   - התוצאות מקובצות לפי הוראה.
5. **API וממשק משתמש:** ממשק REST פשוט וממשק Angular מימין לשמאל.

### טכנולוגיות ונימוק הבחירה
| רכיב | טכנולוגיה | למה |
|---|---|---|
| שרת | .NET 10, ASP.NET Core Minimal API | יציב, מתאים לסביבה ארגונית, ביצועים טובים |
| פענוח Word | DocumentFormat.OpenXml | ה-SDK הרשמי של Microsoft, גישה מלאה למספור ולסגנונות |
| אחסון וחיפוש מילים | SQLite + FTS5 | קובץ יחיד, ללא שרת, BM25 מובנה. מספיק בהיקף של מאות עד אלפי סעיפים |
| חיפוש לפי משמעות | ONNX Runtime + `multilingual-e5-small` | תומך בעברית, רץ מקומית, ללא עלות וללא שליחת מידע החוצה |
| ממשק משתמש | Angular | ממשק SPA עם תמיכה מלאה ב-RTL, וזו גם הטכנולוגיה של האתר הקיים |
| בדיקות | xUnit + מערך 20 השאלות | בדיקות יחידה ומדד איכות חיפוש שחוזר על עצמו |

### היקף ה-POC
פרק 1 – ביצוע תקציב: 34 הוראות בתוקף, 632 סעיפים. מדגם הנתונים נשמר במאגר, כך שאפשר להריץ גם ללא גישה לאתר.
